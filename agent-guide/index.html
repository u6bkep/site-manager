Site Manager

Building a tool you can host here

This page is a guide. If you're an AI assistant whose user shared this link, read it end to end before writing any code — Site Manager has hard limits that will quietly break a normal web project. If you're a human, skim the first two sections and then hand the link to your agent.

What Site Manager is

Site Manager hosts static websites behind your company's Google login. Anyone in your organization who is signed in can visit any site hosted here. Each site has a URL like https://<your-site-manager>/s/<slug>/.

It's designed for tools that run entirely in the browser: dashboards, calculators, form-builders, internal lookup tools, single-page utilities, or any HTML/CSS/JS that doesn't need a server of its own.

What it is not important

The single biggest source of confusion. Site Manager only serves static files. There is no server-side execution of any kind. Specifically, none of these will work:

You can't…Why not
Run Node, Python, PHP, Ruby, or any backendNo runtime — just a file server
Use Next.js / Nuxt / SvelteKit in SSR modeSame reason. Static export only
Have a build step that runs at deploy timeSite Manager does not run npm install or npm run build. You build locally and upload the output
Use API routes (/api/foo) you wrote yourselfThose would need a backend
Connect directly to a databaseNo server; clients can't safely hold DB credentials anyway
Read environment variables / hide secretsEverything in the bundle is visible to anyone who can load the page
Write files on the server, share state between usersNo persistence. Use localStorage for per-user state, or call an external API

What you can do: anything that runs in a browser. Fetch external HTTPS APIs (CORS permitting), use localStorage / IndexedDB for per-user persistence, embed third-party widgets, use any front-end framework after building it down to static files.

For AI agents

Instructions for building a site here

The user wants a tool that runs in the browser. Treat this section as a spec. The rules below are not stylistic preferences — violating them will produce a site that does not work after upload.

1. Default to a single self-contained index.html

For most tools the user will ask for, the right answer is one HTML file with inline <style> and <script> blocks. This is the easiest thing for a non-technical user to upload and redeploy — Site Manager accepts a single .html file directly, no zipping needed. Don't reach for a framework, a bundler, or a multi-file project unless the task genuinely needs it.

2. If you do reach for a framework, build locally first

React, Vue, Svelte, etc. are fine — but Site Manager will not run your build. You must run npm run build (or equivalent) yourself and upload the contents of dist/ (or build/, out/). Configure the framework for static export. Set the base path so it works under /s/<slug>/ (see rule 4).

3. Use relative paths, never absolute

The site is served at /s/<slug>/, not at /. A link or asset reference like /style.css will 404 — it points to the host root, not the site root. Always write style.css or ./style.css. Same for <a href>, <img src>, fetch() URLs that point at sibling files, etc.

4. index.html must sit at the root of the upload

If you ship a single HTML file, this is automatic — Site Manager stores it as index.html regardless of what the file was named locally. If you ship a zip, Site Manager extracts it directly into the site directory, so the zip contents should look like: 

my-tool.zip
├── index.html
├── style.css        (optional)
├── app.js           (optional)
└── assets/          (optional)
    └── logo.png

Not like this — a wrapping folder will break the site because it puts index.html one level too deep: 

my-tool.zip          ← WRONG
└── my-tool/
    └── index.html

The zip command creates the wrong structure if you point it at a folder. Always cd into the folder first, then zip . (see the upload procedure below).

5. There are no secrets

Every byte you ship is visible in the user's browser dev tools. If the user wants to call an API that requires a key, you have three options, in order of preference: (a) use an API that doesn't need a key, (b) ask the user to paste their own key into the page at runtime and store it in localStorage, (c) tell the user this needs a real backend and Site Manager isn't the right home for it.

6. External API calls work, with caveats

fetch() to public HTTPS APIs is fine if the API sends appropriate CORS headers. If it doesn't, the browser will block the request and there's nothing you can do about it from a static page — that's a hard limit, not something to work around with cleverness. Don't suggest a CORS proxy unless the user has one they own.

7. Persistence is per-browser only

localStorage and IndexedDB are scoped to the user's browser. Two coworkers using the same tool will not see each other's data. If the user expects shared state ("we both edit the same list"), surface that limitation immediately — they need a backing service like a Google Sheet, an Airtable, or a real backend.

8. Size and shape limits

  • Single HTML upload is capped at 50 MB.
  • Zip extraction is capped at 500 MB total.
  • No symlinks (they're stripped on extraction).
  • No .. path traversal in zip entries (rejected).
  • The slug is auto-derived from the site name: lowercased, with non-alphanumeric runs collapsed to single hyphens. "My Cool Tool" → my-cool-tool.

9. Walking the user through upload

If you produced a single self-contained HTML file (the recommended path — see rule 1), there's nothing to package. Hand the user the .html file directly and skip to the upload steps below.

Only if your tool has multiple files: from the parent of the site directory (call it ./site/), run: 

cd site && zip -r ../site.zip . && cd ..

The trailing . matters — it zips the contents, not the folder. Then tell the user, in plain language:

  1. Open Site Manager in your browser and sign in with your work Google account.
  2. Click New Tool.
  3. Give it a name (this becomes the URL — keep it short).
  4. Leave Upload File selected.
  5. Drag the .html or .zip file into the drop zone (or click and pick it).
  6. Click Create Tool. It opens to the dashboard; click the new tool to view it.

For updates: open the existing tool, click Update Version, drop the new file. The slug stays the same, so any links the user has shared keep working.

10. The Git option (use only when asked)

Site Manager can also pull from a GitHub repo and auto-redeploy on push. This is the right choice when the user already has a repo, or when the project has multiple files they'll keep editing. To use it: pick GitHub Repo instead of Upload Folder, enter owner/repo, pick a branch, and optionally set a subdirectory (e.g. dist if the built output lives there). The same "no build step on the server" rule applies — Site Manager copies the files as-is. If the user is non-technical and has no opinion, default to upload; it's simpler.

11. When this is the wrong tool

Stop and tell the user if the request needs any of:

  • A real database with shared state
  • User accounts beyond "anyone in the company"
  • Scheduled background jobs
  • Receiving webhooks or sending email
  • Holding API keys that other users shouldn't see

Don't try to fake any of these with client-side hacks. Saying "this needs a real backend" early is more helpful than shipping a broken tool.

For humans: what to do with your agent

Tell your agent what you want to build, and give it the URL of this page. Something like:

"I want a tool that <does X>. Read this page first — it explains what the hosting can and can't do — then build it and walk me through uploading it."

The agent will produce a folder with an index.html inside, zip it, and tell you which file to drop into the upload form on Site Manager. If the agent suggests something the page above says won't work (a backend, a database, hidden API keys), it's worth pushing back or starting over.

A worked example

The simplest possible Site Manager tool — a one-file HTML page with a button that does something useful. Save this to a file and upload it directly; no zipping needed. 

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Word Counter</title>
  <style>
    body { font-family: system-ui, sans-serif; max-width: 600px;
           margin: 3rem auto; padding: 0 1rem; }
    textarea { width: 100%; height: 200px; font-size: 1rem; }
    .stat { display: inline-block; margin-right: 1.5rem; }
  </style>
</head>
<body>
  <h1>Word Counter</h1>
  <textarea id="text" placeholder="Paste text here…"></textarea>
  <p>
    <span class="stat">Words: <b id="words">0</b></span>
    <span class="stat">Characters: <b id="chars">0</b></span>
  </p>
  <script>
    const t = document.getElementById('text');
    t.addEventListener('input', () => {
      const v = t.value;
      document.getElementById('chars').textContent = v.length;
      document.getElementById('words').textContent =
        v.trim() ? v.trim().split(/\s+/).length : 0;
    });
  </script>
</body>
</html>

That's the entire site. One file, no build step, no dependencies, works offline once loaded. Most internal tools should look roughly like this.
